토큰 분류와 질문 답변: 문장 속 어디가 무엇인지

모델 > 언어 모델로 문제 풀기

💡 한 문장으로

문장 분류가 문장마다 라벨 하나를 붙인다면, 토큰 분류는 토큰마다 라벨을 붙여 문장 속 이름, 날짜, 금액을 찾아요(개체명 인식). 메시지에서 질문의 답이 시작하고 끝나는 토큰을 찾으면 질문 답변이에요. 여러 언어를 함께 배운 모델은 한 언어로 배운 것을 다른 언어에도 써요.

🤔 왜 필요할까?

업무 메시지에서 "누가, 어느 회사와, 언제, 얼마"를 뽑아 일정표나 장부에 자동으로 넣고 싶다고 해 봐요. 문장 전체에 라벨 하나를 붙이는 문장 분류로는 안 돼요. 문장 속 어느 부분이 무엇인지 알아야 해요. 이렇게 토큰마다 라벨을 붙이는 일을 토큰 분류라고 하고, 대표가 개체명 인식(NER, Named Entity Recognition)이에요. 메시지와 질문을 주고 답이 되는 부분을 찾게 하면 질문 답변(추출형 QA)이에요.

이 쪽의 예제는 가상의 업무 메시지예요.

🗺️ 통째로 한 번

데이터 → 글자 범위를 토큰 라벨로 → 토큰마다 분류 → 개체 단위 채점 → 글자로 꺼내기 → 영어에 써 보기 → 질문의 답 범위 찾기 → 찾아서 읽기. 상자를 누르면 그 단계로 가요.

① 데이터 읽기

왜 글자 위치로 저장하나? 토큰은 Tokenizer마다 다르게 나뉘어서, 라벨을 토큰 단위로 저장해 두면 모델을 바꿀 때마다 다시 만들어야 해요. 글자 위치는 Tokenizer와 상관없어요. 학습할 때 그 모델의 토큰에 맞춰 바꿔요(②).

test는 train에 없던 문장 틀 4개와 처음 보는 이름(사람 6명, 회사 4곳)으로, en_test는 영어 문장으로 만들었어요. en_test는 학습에 쓰지 않아요.

코드의 ② 부분

② 토큰과 라벨 맞추기

Tokenizer가 알려 주는 토큰마다의 글자 위치를 개체의 글자 범위와 겹쳐 보고, 토큰마다 라벨을 정해요.

왜 어렵나? 이름 하나가 여러 토큰으로 나뉘고("서지아" → 셋), 조사가 이름과 한 토큰으로 묶이기도 해요. 그래서 "토큰의 글자 범위가 개체와 겹치면 그 개체의 토큰"으로 정하고, 개체의 첫 토큰은 B, 나머지는 I를 붙여요. <s>, </s>, 채운 자리는 -100으로 둬서 손실과 채점에서 빼요.

코드의 ③ 부분

③ 토큰마다 분류하는 모델

e5 몸통이 낸 토큰 벡터마다 같은 384 → 9 층을 얹어 라벨 점수를 내고, 정답 라벨로 미세조정해요.

문장 분류는 토큰 벡터를 평균 낸 문장 벡터 하나에 층을 얹었어요. 토큰 분류는 평균 내지 않고, 토큰 벡터 하나하나에 같은 층을 얹어요. 몸통은 똑같고 머리(head)만 바뀌어요. 그래서 이런 모델을 "몸통 + 과제별 머리"로 나눠 불러요. transformers의 AutoModelForTokenClassification이 이 모양을 만들어 줘요.

학습 반복은 문장 분류 ⑤와 같아서 함수 하나(fine_tune)로 묶었어요. ⑦의 질문 답변도 이 함수를 그대로 써요. 바뀌는 건 모델, 데이터를 Tensor로 바꾸는 함수(encode), 손실 함수뿐이에요.

코드의 ⑦ 부분

⑦ 질문 답변: 답의 시작과 끝 찾기

질문과 메시지를 한 줄로 이어 넣고, 메시지의 토큰마다 "답의 시작일 점수"와 "끝일 점수"를 내게 학습해요.

답이 메시지 안에 그대로 있다면, 답을 새로 만들 필요 없이 어디서 시작해 어디서 끝나는지만 고르면 돼요(추출형 QA). 그래서 머리는 384 → 2(시작 점수, 끝 점수)예요. 시작 점수 + 끝 점수가 가장 큰 범위를 답으로 고르고, 시작이 끝보다 뒤인 범위는 빼요.

답이 없으면? 학습할 때 답이 없는 질문은 0번 토큰(<s>)을 시작이자 끝으로 가르쳐요. 쓸 때는 <s>의 점수가 가장 좋은 범위의 점수보다 크면 "답 없음"이라고 해요. 그럴듯한 엉뚱한 답을 내는 것보다 낫기 때문이에요.

질문과 메시지는 <s> 질문 </s></s> 메시지 </s>처럼 한 줄로 들어가요. sequence_ids가 토큰마다 질문(0)인지 메시지(1)인지 알려 줘서, 답은 메시지 쪽에서만 찾아요. 메시지가 모델의 한도(512토큰)보다 길면 겹치게 잘라 여러 번 넣고 가장 좋은 답을 골라요.

코드뜻

logits[..., 0], logits[..., 1]토큰마다 시작 점수, 끝 점수

코드의 ⑧ 부분

⑧ 찾아서 읽기: 메시지 여러 개에서 먼저 찾고, 찾은 메시지에서 답 꺼내기

메시지 12개를 e5 문장 벡터로 바꿔 두고, 질문과 가장 가까운 메시지를 찾은 뒤 ⑦의 모델로 답을 꺼내요.

⑦은 "답이 들어 있는 메시지"를 알려 줘야 했어요. 실제로는 메시지가 수천 개라, 먼저 관련 있는 것을 찾아야 해요. Retriever(찾는 쪽)가 후보를 고르고 Reader(읽는 쪽)가 답을 꺼내는 구조예요. 찾는 쪽은 BM25 같은 단어 검색이나, 질문과 문서를 각각 벡터로 바꾸는 방식(DPR, 여기서는 e5)을 써요.

Reader 자리에 답을 꺼내는 모델 대신 글을 만드는 LLM을 두면 RAG예요. 찾은 문서를 근거로 답을 새로 써요(Embedding과 벡터 검색, Indexing).

🛠️ 실제로 할 때

      
상황어떻게
공개 데이터와 모델NER은 WikiANN(PAN-X), 한국어는 KLUE-NER, 질문 답변은 SQuAD, 한국어는 KorQuAD가 많이 쓰여요. Hub에 이미 미세조정된 모델이 많아서 pipeline("ner"), pipeline("question-answering")으로 바로 써 볼 수 있어요.
채점 도구NER은 seqeval(개체 단위 precision, recall, F1), 질문 답변은 정확히 일치(EM)와, 답과 정답이 겹치는 정도를 재는 F1을 함께 봐요.
한국어 개체의 경계조사가 붙는 문제(⑤)는 형태소 분석기로 미리 나누거나, 글자 단위로 라벨을 붙이거나, 꺼낸 뒤 규칙으로 다듬어요. 어느 쪽이든 "글자 그대로 일치"로 꼭 재 봐요.
여러 언어를 다뤄야 한다다국어 모델(XLM-R, mBERT, e5 다국어판)을 쓰고, 라벨이 많은 언어로 먼저 배운 뒤 다른 언어의 라벨을 조금씩 더하면 효율이 좋아요(⑥). 여러 언어를 섞어 함께 학습하면 각 언어의 점수가 고르게 올라요.
긴 문서의 질문 답변모델 한도(보통 512토큰)를 넘으면 겹치게 잘라(stride) 여러 조각으로 넣고, 조각마다 가장 좋은 답 중에서 골라요.
답을 새로 써야 한다답이 문서에 그대로 없거나 여러 곳을 합쳐야 하면, 꺼내는 모델 대신 생성 모델을 써요(RAG). 대신 근거 없는 답을 지어내지 않는지 검사해요 (Prompt와 출력 계약).
