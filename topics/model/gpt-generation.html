작은 GPT를 처음부터: 학습하고, 고르고, 재기

모델 > 순서와 언어 모델

💡 한 문장으로

GPT는 글만 있으면 다음 토큰 맞히기로 스스로 배워요. 다 배운 뒤에도 다음 토큰을 어떻게 고르느냐에 따라 글이 달라져요. 가장 그럴듯한 것만 고르면 같은 말을 되풀이하고, 확률대로 뽑으면 다양하지만 엉뚱해져서, 상위 후보만 남겨 뽑는 방법을 많이 써요.

🤔 왜 필요할까?

GPT 같은 디코더 모델은 Transformer 구조 ⑧에서 본 대로 "지금까지의 글 → 다음 토큰의 확률"을 내요. 글을 만들려면 그 확률에서 토큰 하나를 고르고, 입력 끝에 붙이고, 다시 계산하기를 되풀이해요. 이 쪽은 두 가지를 직접 해 봐요.

  1. 모델 만들기: 미리 학습된 모델 없이, 글만 가지고 Tokenizer와 GPT를 처음부터 학습해요. 큰 LLM이 만들어지는 과정을 아주 작게 따라가는 거예요.
  2. 고르기: 같은 모델로 다음 토큰을 고르는 방법을 바꿔 가며, 만든 글이 어떻게 달라지는지 숫자로 재요.

학습할 글은 이 노트의 옛 Day 노트예요.

다 만든 모델로 미리 해 보면, 고르는 방법만 바꿔도 이렇게 달라요.

🗺️ 통째로 한 번

말뭉치 정리 → Tokenizer 학습 → 같은 길이로 자르기 → 무작위 GPT → 다음 토큰 맞히기 학습 → 그럴듯하게 고르기 → 확률대로 뽑기 → 만든 글을 숫자로 재기. 상자를 누르면 그 단계로 가요.

🔎 한 단계씩: 설명과 코드를 나란히

코드의 ① 부분

① 말뭉치 읽고 정리하기

Day별 글을 문단으로 펴고, 똑같은 문단은 하나만 남긴 뒤, 20개 중 1개를 valid로 떼어 둬요.

왜 정리부터? 모델은 말뭉치에 있는 것을 그대로 닮아요. 잡음이 많으면 잡음을, 같은 문장이 많으면 그 문장을 외워요. 큰 모델을 만들 때도 말뭉치 정리(중복 제거, 품질 거르기, 개인정보 지우기)에 가장 많은 공을 들여요. 웹에서 모은 글은 같은 페이지가 수없이 겹쳐 있어요.

코드의 ② 부분

② Tokenizer 학습하기

train 글에서 자주 붙어 나오는 조각을 합쳐 가며 어휘 4,000개를 만들어요(BPE).

왜 직접 만드나? 미리 학습된 모델을 쓸 때는 그 모델의 Tokenizer를 그대로 써야 해요. 하지만 처음부터 만든다면, 우리 글에 맞는 Tokenizer가 같은 글을 더 적은 토큰으로 나눠요. 코드 생성 모델이 코드로 Tokenizer를 따로 학습하는 이유도 같아요(들여쓰기, 연산자가 한 토큰이 되게).

BPE(Byte Pair Encoding)는 글자 하나하나에서 시작해, 가장 자주 붙어 나오는 쌍(예: "있"+"어요")을 하나의 새 토큰으로 합치기를 되풀이해요. 정한 어휘 수가 차면 멈춰요. 띄어쓰기는 ▁로 바꿔 글자처럼 다루는 SentencePiece 방식(Metaspace)을 썼어요.

코드 읽기

코드뜻
Tokenizer(models.BPE(unk_token="<unk>"))빈 BPE Tokenizer (tokenizers 라이브러리)
normalizers.NFC()한글 자모가 따로 저장된 글자를 하나로 합치는 유니코드 정리
pre_tokenizers.Metaspace()띄어쓰기를 ▁로
trainers.BpeTrainer(vocab_size=..., special_tokens=[...])어휘 수와 특별 토큰
train_from_iterator(texts, trainer)글 목록으로 학습

왜 이어 붙이나? 문단 길이가 제각각이라 하나씩 넣으면 짧은 문단 뒤를 채워야 해서(padding) 계산이 낭비돼요. 다 이어 붙여 같은 길이로 자르면 채우는 자리가 없어요. 큰 모델도 이렇게 해요.

코드의 ④ 부분

④ 작은 GPT 만들기 (무작위에서 시작)

GPT-2와 같은 구조를 아주 작게 설정해, 가중치를 무작위로 채운 모델을 만들어요.

Hub에서 이름으로 받으면 미리 학습된 가중치까지 오지만, GPT2Config로 설정만 만들어 모델에 넣으면 구조만 같고 가중치는 무작위인 모델이 돼요. 층 수, 칸 수, head 수, 어휘 수, 한 번에 보는 토큰 수를 직접 정해요.

GPT는 다음 토큰 맞히기(CLM, Causal Language Modeling)로 배워요. BERT, e5 같은 인코더는 가운데를 가리고 맞히기(MLM)로, T5 같은 인코더-디코더는 입력을 받아 다른 글 만들기로 배워요. 무엇을 만들 모델이냐에 따라 목표를 골라요.

코드뜻

GPT2LMHeadModel(config)설정대로 무작위 가중치 모델 (LM head: 마지막 벡터 → 어휘 수만큼 점수)

코드의 ⑤ 부분

⑤ 학습하기: 다음 토큰 맞히기

train 줄에서 무작위로 32줄씩 뽑아 1,000걸음 학습하고, 200걸음마다 valid 손실을 재요.

학습률은 처음 10% 동안 키웠다가 끝까지 천천히 줄여요(OneCycle). 처음부터 크게 움직이면 무작위 상태에서 튀기 쉽고, 끝에서는 작게 움직여야 바닥에 자리 잡아요. 기울기가 너무 크면 1로 잘라요(clip_grad_norm_). Transformer 학습에서 흔한 안정 장치예요.

큰 모델은 GPU 여러 대에 같은 모델을 하나씩 두고 데이터를 나눠 계산한 뒤 기울기를 모아 합쳐요(분산 데이터 병렬, DDP). 하는 일은 이 반복과 같아요.

코드 읽기

코드뜻
torch.optim.lr_scheduler.OneCycleLR(...)걸음마다 학습률을 키웠다 줄이기
torch.nn.utils.clip_grad_norm_(..., 1.0)기울기 전체의 크기가 1을 넘으면 1로 줄이기
X_train[torch.randint(0, len(X_train), (32,))]무작위로 32줄 뽑기

코드의 ⑥ 부분

⑥ 고르는 방법 1: 가장 그럴듯한 것 고르기 (greedy, beam)

앞부분 6개에 이어 30토큰을 쓰게 하고, 매번 확률이 가장 높은 토큰을 고르는 방법과 후보 5개를 함께 따라가는 방법을 비교해요.

greedy는 매 걸음 확률 1등 토큰을 골라요. 빠르지만 지금 1등이 전체 글로 보면 최선이 아닐 수 있어요. beam search는 지금까지 이어 쓴 후보 B개(여기서는 5)를 함께 들고 가다가, 걸음마다 후보들의 다음 토큰을 모두 펼쳐 "전체 확률(log 확률의 합)"이 높은 B개만 남겨요. 마지막에 가장 높은 하나를 골라요.

왜 반복하나? 한 번 나온 말이 다시 나오면, 모델은 앞에서 본 걸 참고해 같은 말을 또 높게 쳐요. 확률만 좇으면 이 고리에서 못 빠져나와요. 그래서 같은 n-토큰 묶음이 두 번 나오지 못하게 막는 옵션(no_repeat_ngram_size)을 같이 써요.

코드 읽기

코드뜻
gpt.generate(inp, max_new_tokens=30, do_sample=False)greedy
num_beams=5후보 5개를 함께 따라가기
no_repeat_ngram_size=33-토큰 묶음 반복 금지
logits.log_softmax(-1).gather(...)실제로 고른 토큰의 log 확률 꺼내기 (뜻밖의 정도 계산)

이 단계까지 실행하면

코드의 ⑦ 부분

⑦ 고르는 방법 2: 확률대로 뽑기 (temperature, top-k, top-p)

다음 토큰의 확률대로 무작위로 뽑되, temperature로 확률을 뾰족하게 하거나 상위 후보만 남겨 뽑아요.

sampling은 확률이 0.3인 토큰은 30% 확률로 뽑아요. 같은 앞부분에서도 매번 다른 글이 나와요. temperature는 점수를 t로 나눠 확률을 다시 만들어요. 1보다 작으면 1등에 더 몰리고, 크면 고르게 퍼져요.

문제는 확률이 아주 낮은 토큰 수천 개를 다 합치면 꽤 큰 몫이 된다는 거예요. 그 꼬리에서 하나만 뽑혀도 글이 엉뚱해져요. top-k는 상위 k개만 남기고, top-p(nucleus)는 확률을 큰 순서로 더해 p(예: 0.9)를 넘을 때까지만 남겨요. top-p는 확신할 때는 후보가 몇 개뿐이고, 헷갈릴 때는 많아져서 상황에 맞게 바뀌어요.

코드 읽기

코드뜻
do_sample=True, top_k=0, temperature=0.7자르지 않고 t=0.7로 뽑기 (top_k=0: 자르기 끔)
top_k=20상위 20개 중에서 뽑기
top_p=0.9누적 확률 0.9까지의 후보에서 뽑기

코드의 ⑧ 부분

⑧ 요약과 평가: 본문에서 대표 문장 고르기와 ROUGE

주제 페이지마다 본문의 첫 문장과, 본문 전체와 뜻이 가장 가까운 문장을 골라 사람이 쓴 '한 문장' 요약과 ROUGE로 비교해요.

만든 글이 좋은지는 결국 사람이 봐야 하지만, 매번 그럴 수는 없어서 정답 글과 겹치는 조각으로 재요. BLEU는 만든 글의 조각 중 정답에 있는 비율(정밀도)을 중심으로 재서 번역에 쓰고, ROUGE는 정답의 조각 중 만든 글에 있는 비율(재현율)을 중심으로 재서 요약에 써요. 요약은 "중요한 내용을 빠뜨리지 않았나"가 중요하니까요. ROUGE-L은 순서까지 맞는 가장 긴 공통 부분으로 재요.

한계도 분명해요. 같은 뜻을 다른 말로 쓰면 0점에 가깝고, 말이 겹쳐도 틀린 내용일 수 있어요. 그래서 숫자와 함께 사람이 직접 읽어 봐요.

코드 읽기

코드뜻
Counter(c) & Counter(r)두 조각 목록에서 겹치는 개수 (적은 쪽 기준)
lcs[i + 1][j + 1] = ...가장 긴 공통 부분 순서 길이를 표로 채우기 (ROUGE-L)
v @ F.normalize(v.mean(0), dim=0)문장마다 본문 평균 벡터와의 코사인 유사도

🛠️ 실제로 할 때

      
상황어떻게
실제 LLM을 처음부터 만든다면수천억에서 수조 토큰의 말뭉치, 수십억 개 이상의 가중치, GPU 수백에서 수천 대가 필요해요. 그래서 대부분은 공개된 사전학습 모델을 받아 미세조정하거나, API로 써요. 처음부터 만드는 건 분야가 아주 특수하거나(예: 코드, 특정 언어) 데이터를 밖에 낼 수 없을 때예요.
말뭉치가 너무 커서 디스크에 안 들어간다load_dataset(..., streaming=True)로 한 줄씩 흘려 읽으며 학습해요. 디스크에 다 받지 않아도 돼요.
디코딩 설정을 고를 때사실을 정확히 답해야 하면 temperature를 낮게(0~0.3) 또는 greedy, 글쓰기와 대화는 top-p 0.9, temperature 0.7 안팎에서 시작해요. 반복이 보이면 반복 벌점(repetition_penalty)을 줘요.
API의 temperatureLLM API의 temperature, top_p가 바로 ⑦의 값이에요 (LLM API 클라이언트). 같은 질문에 답이 매번 다른 이유예요.
요약 모델기사 요약은 BART, PEGASUS(문장을 통째로 가리고 되살리기로 미리 학습해 요약에 강함), 여러 과제를 "글 → 글"로 통일한 T5가 대표예요. 대화 요약처럼 말투가 다른 글은 그 분야 데이터로 미세조정해야 해요.
생성 결과를 재는 방법요약은 ROUGE, 번역은 BLEU, 언어 모델 자체는 perplexity를 많이 써요. 숫자는 비교용이고, 최종 판단은 사람이 읽어 보거나, 기준을 정해 다른 LLM에게 채점시키기도 해요.
