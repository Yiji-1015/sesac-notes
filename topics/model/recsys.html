모델 > 추천과 평생 학습

💡 한 문장으로

이용 기록 표의 빈칸 중 볼 만한 것을 골라요. 같이 본 기록으로 닮은 것을 찾는 협업 필터링, 숨은 취향 벡터를 찾는 행렬 분해, 닫힌 식의 EASE, 그래프의 LightGCN을 상위 k개 지표로 비교하고, 인기 편향과 콜드 스타트를 함께 봐요.

🤔 왜 필요할까?

음악, 영상, 쇼핑, 채용 공고처럼 고를 것이 수만 개일 때, 사용자마다 볼 만한 몇 개를 골라 주는 게 추천 시스템이에요. 분류처럼 정답 표가 있지 않고, 사람들이 무엇을 봤는지(이용 기록)에서 취향을 짐작해요.

분류 (머신러닝 기초)추천
데이터행마다 정답이 있는 표사용자 × 아이템 이용 기록, 대부분 빈칸
예측이 행의 답이 사람이 아직 안 본 것 중 좋아할 순서
빈칸의 뜻-싫어한다가 아니라 "모른다" (암묵적 피드백)
평가정확도, F1상위 k개의 정밀도, 재현율, NDCG, 다양성

이 쪽은 사용자마다 숨은 장르 취향을 정해 둔 가상 기록으로, 고전적인 방법부터 그래프 모델까지 같은 지표로 비교해요. 진짜 취향을 아니까 "가장 잘해도 이 정도"인 천장도 잴 수 있어요.

🗺️ 통째로 한 번

기록과 나누기 → 지표와 기준선 → 이웃 → 숨은 취향 벡터 → 닫힌 식 → 그래프 → 편향. 상자를 누르면 그 단계로 가요.

코드는 examples/recsys/recommend.py 하나예요. CPU로 10초 남짓 걸려요.

🔎 한 단계씩: 설명과 코드를 나란히

코드의 ① 부분

① 이용 기록 만들고 나누기

사용자마다 장르 취향, 아이템마다 장르와 인기도를 정해 이용 기록을 만들고, 사용자마다 30%를 숨겨 정답으로 둬요.

평점처럼 "얼마나 좋았는지"를 직접 받은 것은 명시적 피드백, 봤다, 눌렀다, 샀다처럼 행동만 남은 것은 암묵적 피드백이에요. 실제 서비스는 대부분 암묵적이라 여기서도 "봤다"만 있어요.

나눌 때는 사용자마다 일부를 숨겨요. 행을 통째로 나누면 test 사용자의 기록이 하나도 없어 추천할 수 없어요. 시간이 있는 데이터면 마지막 몇 개를 숨겨서 "과거로 미래 맞히기"를 해요.

코드의 ② 부분

② 평가 지표와 인기순 기준선

사용자마다 10개를 추천하고, 숨긴 정답이 몇 개 들어 있는지와 몇 번째에 있는지로 채점해요.

정밀도@k: 추천 k개 중 정답 비율. 재현율@k: 정답 중 k개 안에 든 비율. NDCG@k: 위에 있을수록 크게 쳐서(1 ÷ log₂(순위 + 1)) 더한 뒤, 가장 잘 늘어놓았을 때 값으로 나눈 것이에요. 순서까지 보는 지표라 추천에서 가장 많이 써요. 이 밖에 MAP, MRR(첫 정답의 순위 역수), AUC도 써요. 그리고 정확도만 보면 모두 인기 아이템만 받게 되니, 커버리지(추천에 한 번이라도 나온 아이템 비율)나 다양성을 같이 봐요.

코드의 ③ 부분

③ 이웃으로 추천하기: 협업 필터링

같은 사람들이 함께 본 아이템일수록 닮았다고 보고, 내가 본 것과 닮은 아이템을 추천해요.

협업 필터링은 아이템 내용을 보지 않고 "나와 비슷한 사람들의 기록"만으로 추천해요. 아이템 기반: 아이템을 "본 사람들" 벡터로 보고 코사인 유사도를 구한 뒤, 내가 본 아이템들과의 유사도를 더해 점수를 매겨요. 사용자 기반: 나와 닮은 사용자들이 본 것을 모아요. 아이템 수가 사용자 수보다 적고 덜 바뀌는 서비스에서는 아이템 기반이 계산과 설명("이걸 본 사람들이 본")에 유리해요.

코드 읽기

코드뜻
cosine(X)열(아이템)끼리 코사인 유사도, 자기 자신은 0
X @ item_sim내가 본 아이템들과의 유사도 합
user_sim @ X닮은 사용자들의 기록을 유사도만큼 섞기
코드의 ④ 부분

④ 숨은 취향 찾기: 행렬 분해 (BPR)

사용자와 아이템을 64칸 벡터로 두고, 내적이 "본 것 > 안 본 것"이 되게 배워요.

행렬 분해는 사용자 × 아이템 표를 (사용자 × d) 행렬과 (d × 아이템) 행렬의 곱으로 근사해요. d칸 벡터는 사람이 정하지 않은 숨은 취향 축이에요(이 데이터라면 장르 비슷한 것). 점수는 두 벡터의 내적이에요.

암묵적 피드백에서는 빈칸이 정답 0이 아니라서, 점수 자체를 맞히는 대신 순서를 배워요. BPR은 "본 아이템 i의 점수가 아무거나 뽑은 아이템 j보다 크다"의 확률 σ(점수ᵢ − 점수ⱼ)를 키워요. 안 본 것을 뽑아 쓰는 걸 음성 샘플링이라고 해요.

코드 읽기

코드뜻
P, Q사용자 벡터, 아이템 벡터 (각 64칸)
x = (P[u] * (Q[i] - Q[j])).sum(dim=1)본 것 점수 − 뽑은 것 점수
-logsigmoid(x)BPR 손실: 순서가 맞을수록 작아요
reg * (...)벡터가 커지지 않게 누르는 규제

코드의 ⑤ 부분

⑤ 닫힌 식 하나로: EASE

아이템 × 아이템 가중치 B를 "내가 본 것들로 각 아이템을 다시 만들기"로 두고, 역행렬 하나로 한 번에 풀어요.

EASE는 은닉층이 없는 아주 얕은 AutoEncoder예요. 사용자 기록 x를 넣어 xB로 다시 만들되, 아이템이 자기 자신을 베끼지 못하게 B의 대각선을 0으로 묶어요. 이 문제는 B = I − P × diag(1 ÷ diag(P)), P = (XᵀX + λI)⁻¹로 한 번에 풀려서 학습 반복이 없어요. 아이템이 수만 개를 넘으면 역행렬이 무거워져요.

코드 읽기

코드뜻
np.linalg.inv(X.T @ X + lam * np.eye(I))P = (XᵀX + λI)의 역행렬
-P / np.diag(P)[None, :]열마다 대각 값으로 나누기
np.fill_diagonal(B, 0)자기 자신 베끼기 금지

코드의 ⑥ 부분

⑥ 이용 기록을 그래프로: LightGCN

사용자와 아이템을 노드로, 본 기록을 선으로 그린 그래프에서 이웃 벡터를 모아 행렬 분해를 강화해요.

이용 기록은 사용자와 아이템 사이에만 선이 있는 그래프예요. GNN처럼 이웃 벡터를 모으면 1층에서 "내가 본 아이템", 2층에서 "그걸 본 다른 사람들", 3층에서 "그 사람들이 본 아이템"까지 정보가 와요. NGCF는 여기에 가중치와 활성화 함수를 넣었는데, LightGCN은 그걸 빼고 정규화한 합만 남겼더니 더 잘 됐어요. 층마다의 벡터를 평균 내서 최종 벡터로 써요.

코드뜻

h = A_norm @ h이웃 벡터 모으기 (가중치, 활성화 없음)
torch.stack(out).mean(dim=0)0층부터 마지막 층까지 평균

코드의 ⑦ 부분

⑦ 기록이 적은 사용자와 인기 편향

기록 수로 사용자를 셋으로 나눠 점수를 보고, 추천 목록이 인기 아이템으로 얼마나 기우는지 재요.

더 나아간 추천들: 행렬 분해의 내적을 신경망으로 바꾼 NCF, 사용자 기록을 통째로 넣고 다시 만드는 AutoRec과 Multi-VAE(생성 모델의 VAE), 아이템 내용이나 사용자 정보(나이, 장르, 지식 그래프)를 함께 넣는 Wide & Deep, 본 순서를 BERT처럼 가려 맞히는 BERT4Rec이 있어요. 서비스에서는 수백만 개 중 수백 개를 빨리 고르는 후보 생성(사용자와 아이템 벡터의 근사 최근접 검색, 임베딩 검색)과 그 수백 개를 꼼꼼히 순서 매기는 랭킹 두 단계로 나눠요.

LLM으로 추천하기: 음악을 오디오 토큰과 글 토큰으로 바꿔 LLM이 대화로 추천하게 하는 시도도 있어요. "비 오는 날 듣기 좋은, 기타 위주 90년대 노래"처럼 말로 한 요청과 콜드 스타트에 강하지만, 아이템이 수십만 개면 결국 검색과 함께 써요.

🛠️ 실제로 할 때

      
상황어떻게
어디서부터인기순 → 아이템 이웃 → EASE를 먼저 같은 나누기와 지표로 재고, 학습형 모델은 그걸 넘을 때만 들여요(③).
오프라인 점수와 실제숨긴 기록 맞히기는 "원래 볼 것"을 맞히는 거라, 새로운 걸 발견하게 해 주는 추천은 낮게 나와요. 최종 판단은 A/B 검정으로(가설 검정).
새 사용자, 새 아이템협업 필터링은 기록이 없으면 못 써요. 가입 때 관심사 묻기, 인기순, 아이템 내용 기반 추천을 섞어 시작해요.
추천이 한쪽으로 몰린다인기 편향(⑦), 비슷한 것만 계속 보여 주는 문제가 생겨요. 다양성 점수를 섞거나 탐색(강화학습의 밴딧)을 넣어요.
