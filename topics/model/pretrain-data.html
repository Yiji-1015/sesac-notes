LLM의 학습 데이터 만들기: 거르고, 빼고, 섞기

모델 > LLM 학습 데이터와 평가

💡 한 문장으로

LLM을 학습하기 전에 규칙으로 거르고, 똑같은 것과 거의 같은 것(MinHash)을 빼고, 분야를 어떤 비율로 섞을지 정해요. 섞는 비율은 토크나이저의 압축률을 바꿔서, 한국어처럼 적게 섞인 언어는 토큰이 많이 들어요. 비율은 작은 대리 실험의 순위를 믿고 회귀로 골라요.

🤔 왜 필요할까?

LLM의 성능은 모델 구조보다 무엇을 얼마나 깨끗하게, 어떤 비율로 보여 줬나에 더 크게 갈려요. 그런데 처음부터 학습 한 번에 몇 주와 큰돈이 들어서, 데이터의 선택을 하나하나 큰 모델로 시험해 볼 수 없어요. 그래서 데이터 쪽 결정은 대부분 싸게 미리 재 보고 정해요.

정할 것여기서 재 보는 것이 쪽
무엇을 버릴까규칙이 버린 것을 직접 읽기②
겹치는 글똑같은 것, 거의 같은 것③④
토크나이저분야마다 압축률⑤
무엇을 얼마나 섞을까작은 실험의 순위를 믿고 회귀로 고르기⑥⑦

작은 GPT에서 말뭉치를 정리하고 BPE를 배웠다면, 이 쪽은 그 선택들을 숫자로 재 봐요. 한국어 서비스라면 특히 ⑤⑦이 비용과 바로 이어져요.

🗺️ 통째로 한 번

모으기 → 규칙으로 거르기 → 똑같은 것 빼기 → 거의 같은 것 빼기 → 토크나이저의 압축률 → 섞는 비율 바꾸기 → 비율 고르기. 상자를 누르면 그 단계로 가요.

코드는 examples/pretrain_data/mix_tokenizer.py 하나예요. 받을 파일 없이 이 노트의 한국어 글과 파이썬 표준 라이브러리로 말뭉치를 만들어요.

코드의 ② 부분

② 규칙으로 거르기

너무 짧은 것, 기호와 숫자가 대부분인 것, 같은 단어가 되풀이되는 것을 버려요.

웹 문서에는 메뉴, 광고, 표 조각, 자동 생성 글이 섞여 있어요. 가장 먼저 쓰는 건 이런 규칙(휴리스틱) 거르기예요. 빠르고 설명하기 쉽지만, 기준 하나가 좋은 글까지 버릴 수 있어요. 그다음에 품질 분류기(좋은 글을 닮았나를 맞히는 작은 모델)를 더 쓰기도 해요.

코드의 ③ 부분

③ 똑같은 것 빼기

완전히 같은 문단은 처음 나온 하나만 남겨요.

코드의 ④ 부분

④ 거의 같은 것 빼기: MinHash

단어 5개짜리 조각들의 집합으로 문단을 보고, 두 집합이 얼마나 겹치는지(Jaccard)를 지문 64칸으로 빠르게 어림해요.

한두 단어만 다른 글은 해시가 달라서 ③으로 못 잡아요. 두 문단의 조각 집합이 얼마나 겹치는지를 Jaccard 유사도(겹치는 조각 수 ÷ 합친 조각 수)로 재면 되지만, 모든 짝을 비교하면 문단 수의 제곱만큼 걸려요.

MinHash는 해시 함수 하나로 조각들을 섞어 가장 작은 값만 남겨요. 두 집합의 가장 작은 값이 같을 확률이 정확히 Jaccard 유사도라서, 해시 64개의 "가장 작은 값" 64칸(지문)이 몇 칸 같은지로 유사도를 어림해요. LSH는 지문을 4칸씩 16묶음으로 나눠 한 묶음이라도 똑같은 짝만 후보로 골라, 대부분의 짝을 비교하지 않고 넘어가요.

코드뜻

코드의 ⑤ 부분

⑤ 토크나이저의 압축률

가진 비율대로 섞은 글로 BPE 토크나이저를 배우고, 분야마다 토큰 하나가 몇 글자를 담는지 재요.

압축률은 같은 글을 몇 개의 토큰으로 바꾸나예요. 압축률이 높으면 같은 글이 적은 토큰이 돼서, 학습과 추론이 싸지고 문맥 창에 더 많이 들어가요. BPE는 학습 글에서 자주 붙어 나오는 조각부터 합치기 때문에, 학습 글에 적게 들어간 분야는 잘게 쪼개져요.

여기서는 바이트 단위 BPE(GPT-2 방식)를 써요. 처음 어휘가 바이트 256개라서 어떤 글자도 모르는 토큰이 되지 않지만, 합쳐진 조각이 없으면 한글 한 글자가 바이트 3개로 쪼개져요.

코드뜻

trainers.BpeTrainer(vocab_size=4000)자주 붙는 조각을 어휘 4,000개가 될 때까지 합치기
len(text) / len(tok.encode(text).ids)압축률: 토큰 하나에 담긴 글자 수

코드의 ⑥ 부분

⑥ 섞는 비율을 바꾸면: 작은 대리 토크나이저

비율 조합 24가지로 토크나이저를 두 크기로 배우고, 작은 쪽의 순위가 큰 쪽에서도 그대로인지 봐요.

최적의 비율을 찾으려면 비율마다 토크나이저를 배워 봐야 하는데, 실제 크기(어휘 수만 개, 글 수백 GB)로는 비싸요. TReX는 작은 대리(proxy) 토크나이저로 많은 조합을 시험하고, 그 순위가 큰 토크나이저에서도 유지된다는 걸 확인한 뒤 써요. 같은 생각을 데이터 섞기 전체에 쓰는 방법(작은 모델로 비율을 시험하고 회귀로 고르기)도 있어요.

코드의 ⑦ 부분

⑦ 회귀로 비율 고르기

대리 토크나이저의 결과로 "비율 → 압축률" 회귀를 맞추고, 서비스 글의 토큰 수가 가장 적은 비율을 골라 실제 크기로 확인해요.

무엇을 기준으로 "좋은 비율"인지부터 정해야 해요. 여기서는 서비스에 들어올 글(한국어 60%, 영어 20%, 코드 20%) 1,000자에 드는 토큰 수를 줄이는 게 목표예요. 분야마다 압축률을 로그 비율의 직선으로 근사하고, 비율 격자 전체에서 예측이 가장 좋은 점을 골라요.

🛠️ 실제로 할 때

      
상황어떻게
한국어 서비스를 만든다쓸 모델의 토크나이저로 우리 글의 압축률부터 재요. 같은 내용이 모델마다 1.5배 넘게 토큰이 차이 날 수 있고, 그게 곧 비용과 문맥 길이예요.
말뭉치를 거른다규칙은 분야마다 따로 맞추고, 버린 것과 남긴 것을 무작위로 뽑아 꼭 읽어요. 중복 빼기는 거의 항상 이득이에요.
데이터를 섞는다"가진 만큼"이 아니라 쓰일 곳의 비율에서 출발해요. 조합이 많으면 작은 실험의 순위를 믿고 회귀로 고르고, 마지막 후보만 크게 확인해요.
