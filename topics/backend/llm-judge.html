LLM으로 답 채점하기: LLM-as-a-Judge

백엔드 > LLM 활용

💡 한 문장으로

채점 기준(루브릭)과 점수 모양을 정하고, 고정된 기준은 캐시해서 수천 건을 싸게 채점해요. 채점자도 버릇이 있어서, 순서를 바꿔 묻고 사람 점수와 맞춰 봐야 믿을 수 있어요.

🤔 왜 필요할까?

LLM이 만든 답이 좋은지 어떻게 알까요? 사람이 다 읽으면 정확하지만 느리고 비싸요. 작은 GPT와 디코딩 ⑧의 ROUGE처럼 기준 답과 겹치는 단어를 세면 빠르지만, 뜻은 같은데 말이 다른 답을 깎아요. 그 사이에 있는 방법이 LLM을 채점자로 쓰는 것(LLM-as-a-Judge)이에요.

채점자도 LLM이라서 Prompt와 출력 계약, LLM API 클라이언트에서 본 것을 그대로 써요. 이 쪽에서는 거기에 채점만의 문제를 더해요.

문제이 쪽
채점 기준을 어떻게 적고, 점수를 어떤 모양으로 받나①
같은 기준으로 수천 건을 채점할 때 비용②③ 프롬프트 캐시
생각하다 잘린 답, 거절④
채점자의 버릇(순서, 길이, 후함)과 사람 점수와의 일치⑤

🗺️ 통째로 한 번

채점 기준을 점수 계약으로 → 고정 부분을 캐시하는 요청 → 비용 계산 → 응답 읽기 → 채점을 믿을 수 있는지 확인. 상자를 누르면 그 단계로 가요.

예제는 Anthropic Python SDK로 Claude Opus 5.5를 불러요. 이 노트의 값은 가짜 서버를 SDK에 붙여 실제로 실행한 결과예요. SDK가 만드는 요청과 응답 처리 코드는 진짜지만, 판정 내용과 토큰 수는 가짜 서버가 돌려준 고정 값이라 모델의 실제 판단이 아니에요.

🔎 한 단계씩: 설명과 코드를 나란히

코드의 ① 부분

① 채점 기준과 점수 계약

무엇을 몇 점으로 볼지 글로 적고(루브릭), 받을 답의 모양을 Pydantic 클래스로 정해요.

루브릭은 점수마다 무엇을 뜻하는지 적은 채점 기준표예요. "좋으면 5점"처럼 막연하면, 같은 답도 부를 때마다 점수가 달라져요. 점수마다 구체적인 조건을 적고, 기준 답을 함께 줘서 "무엇과 비교할지"를 정해요.

채점 방식은 크게 둘이에요. 답 하나에 점수를 매기는 점수 매기기(이 쪽 ①~④)와, 두 답 중 나은 쪽을 고르는 둘 중 고르기(⑤)예요. 둘 중 고르기가 더 안정적이지만, 답이 n개면 비교가 n²에 가깝게 늘어요.

받는 모양은 Prompt와 출력 계약 ③처럼 Pydantic으로 적어요. 채점에서는 두 가지를 더 신경 써요.

  • 근거를 점수보다 먼저: 모델은 앞에서부터 차례로 써요. 점수를 먼저 쓰면 그 뒤의 근거가 점수에 맞춰져요.
  • 고를 수 있는 값을 정해 두기: 점수와 오류 종류를 정해진 값 중에서만 고르게 하면, 모아서 세기 쉬워요.

코드 읽기

코드뜻
class Verdict(BaseModel)받을 판정의 모양
Literal[1, 2, 3, 4, 5]점수는 이 다섯 값 중 하나
ConfigDict(extra="forbid")계약에 없는 필드는 거절
Verdict.model_json_schema()클래스를 API에 줄 JSON Schema로 바꾸기

코드의 ② 부분

② 요청 만들기: 고정 부분은 앞에, 바뀌는 부분은 뒤에

채점 기준은 system에 두고 캐시 표시를 붙이고, 문항은 messages에 넣어요. 답의 모양과 생각 깊이는 output_config로 정해요.

프롬프트 캐시: 요청의 앞부분이 이전 요청과 글자 하나까지 같으면, 서버가 그 부분을 다시 계산하지 않고 저장해 둔 결과를 읽어요. 읽은 토큰은 훨씬 싸고, 첫 글자가 나오기까지의 시간도 줄어요. 요청은 tools → system → messages 순서로 이어 붙여지니까, 안 바뀌는 것을 앞에 두고 cache_control로 "여기까지 저장"을 표시해요.

⚠️ 캐시가 깨지는 흔한 이유: 채점 기준에 오늘 날짜나 요청 번호를 넣기, 예시 순서를 매번 섞기, 키 순서가 바뀌는 JSON. 그리고 앞부분이 너무 짧으면(Claude Opus 5.5는 512토큰 미만) 표시를 해도 저장되지 않아요. 오류도 나지 않으니 응답의 usage.cache_read_input_tokens가 0인지로 확인해요.

output_config에는 두 가지를 넣어요. format은 ①의 JSON Schema로 답의 모양을 강제하고, effort는 생각을 얼마나 깊이 할지예요(low~max). 채점은 기준이 분명하면 low로도 충분한 경우가 많아서, 몇십 건으로 사람 점수와 비교해 보고 정해요.

예전 예제는 같은 답이 나오게 temperature=0을 주곤 했는데, Claude Opus 5.5 같은 최신 Claude 모델은 temperature를 받지 않아요(보내면 오류). 판정이 흔들리는지는 같은 문항을 몇 번 다시 채점해서 직접 재요.

코드 읽기

코드뜻
anthropic.Anthropic(max_retries=2)키는 환경 변수 ANTHROPIC_API_KEY에서. 실패하면 2번까지 다시
system=[{..., "cache_control": {"type": "ephemeral"}}]여기까지를 5분 동안 저장. "ttl": "1h"면 1시간
output_config={"effort": ..., "format": {"type": "json_schema", ...}}생각 깊이와 답의 모양
b.type == "text"생각(thinking) 블록은 건너뛰고 글 블록만 읽기

코드의 ③ 부분

③ 캐시로 비용 줄이기: 몇 건부터 이득인가

캐시에 저장할 때는 조금 더 내고, 읽을 때는 훨씬 적게 내요. 문항 수에 따라 전체 비용을 계산해요.

캐시 값은 세 가지예요. 저장하지 않은 입력은 보통 단가, 처음 저장할 때는 입력 단가의 1.25배(5분) 또는 2배(1시간), 저장된 것을 읽을 때는 훨씬 싸요(Claude Opus 5.5는 0.05배). 출력 토큰은 캐시와 상관없어요.

읽을 때마다 저장 시간이 다시 5분으로 늘어나요. 그래서 같은 기준으로 5분 안쪽 간격으로 계속 채점하면 5분짜리로 충분하고, 몇십 분씩 쉬었다 하면 1시간짜리가 나아요.

코드 읽기

코드뜻
fixed * WRITE_5M + (n - 1) * fixed * READ첫 건은 저장 값, 나머지 n − 1건은 읽기 값
n * varying바뀌는 문항 부분은 매번 보통 단가

코드의 ④ 부분

④ 응답 읽기: 잘린 답, 거절, 쓴 토큰 모으기

stop_reason을 먼저 보고, 잘렸으면 한도를 키워 한 번만 다시 묻고, 모든 호출의 사용량을 더해요.

답의 모양이 맞는지 검사하고 틀리면 한 번 다시 묻는 건 Prompt와 출력 계약 ④⑥에서 봤어요. format으로 모양을 강제하면 그런 일은 드물어요. 대신 채점에서는 다른 두 경우를 먼저 봐요.

  • stop_reason == "max_tokens": 생각에 토큰을 쓰다 한도에 닿아 JSON이 중간에 끊겼어요. 한도를 키워 다시 물어요.
  • stop_reason == "refusal": 안전 판단으로 답하지 않았어요. 다시 물어도 같기 쉬워서, 점수 없음으로 남기고 사람이 봐요.

코드 읽기

코드뜻
for max_tokens in (2048, 8192)처음엔 2,048, 잘리면 8,192로 한 번만 더
r.stop_reason왜 멈췄나: end_turn(다 씀), max_tokens(한도), refusal(거절)
total_usage(used)모든 호출의 입력, 캐시 쓰기, 캐시 읽기, 출력 토큰을 따로 더하기

이 단계까지 실행하면

코드의 ⑤ 부분

⑤ 채점을 믿을 수 있나: 순서 바꿔 묻기, 사람 점수와 맞춰 보기

두 답의 자리를 바꿔 한 번 더 물어 판정이 뒤집히는지 보고, 사람이 매긴 점수와 얼마나 맞는지 숫자로 재요.

LLM 채점자에게는 알려진 버릇이 있어요.

버릇모습줄이는 방법
자리 버릇같은 두 답도 먼저(또는 나중에) 나온 쪽을 더 고름순서를 바꿔 두 번 묻고, 뒤집히면 "같음"
길이 버릇길고 자신 있게 쓴 답을 더 좋게 봄루브릭에 "길이는 보지 마"를 넣고, 기준 답과 비교하게
자기 편자기와 같은 모델이 쓴 답을 더 좋게 봄채점 모델을 답한 모델과 다르게, 또는 여러 모델의 판정을 모으기
후함점수가 전체로 높게 몰림사람 점수 몇십 건과 맞춰 평균 차이를 보고 기준을 다시 잡기

사람 점수와 맞춰 보기: 채점자를 쓰기 전에 몇십 건을 사람이 먼저 채점하고, 같은 문항을 채점자에게 매겨 비교해요. 완전 일치만 보면 4점과 5점의 작은 차이도 틀린 걸로 쳐서 너무 박하고, 그냥 상관계수를 보면 "늘 1점씩 후함"을 못 잡아요. 그래서 가중 kappa(우연히 맞을 몫을 빼고, 크게 어긋날수록 더 깎은 일치도)와 평균 차이를 함께 봐요.

사람끼리도 점수가 다 같지는 않아요. 사람 두 명의 kappa를 먼저 재서, 채점자가 "사람끼리 맞는 만큼" 맞으면 쓸 만하다고 봐요. 기준 답이 하나뿐이면 다르게 말한 좋은 답이 깎이니까, 기준 답을 여러 개 주기도 해요. 그리고 채점자를 쓴 뒤에도 일부는 계속 사람이 다시 봐요(사람이 고리 안에 남기).

🛠️ 실제로 할 때

      
상황어떻게
채점 기준이 길다예시 답과 점수를 몇 개 넣으면 좋아지지만 길어져요. 고정 부분이라 캐시되니, 길이보다 기준이 바뀌지 않게 하는 게 중요해요.
수천 건을 한꺼번에 채점급하지 않으면 Message Batches로 보내면 값이 절반이에요. 응답은 순서가 섞여 오니 custom_id로 맞춰요.
채점 모델 고르기사람 점수 몇십 건으로 모델과 effort를 바꿔 가며 kappa를 재서, 맞는 것 중 가장 싼 조합을 골라요.
점수가 문항마다 흔들린다같은 문항을 3번 채점해 다르게 나온 비율을 재요. 많으면 루브릭의 점수 경계를 더 구체적으로 적어요.
기준 답이 없다두 답 중 고르기로 바꾸거나, 루브릭에 꼭 들어가야 할 항목을 하나씩 적고 "있다 / 없다"로 체크하게 해요.
