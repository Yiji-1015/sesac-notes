💡 한 문장으로

서비스 구현은 기능 코드에 실행 조건, 자원 수명, 저장 책임, 검증 순서를 연결해서 같은 결과를 다시 확인할 수 있게 만드는 일이에요.

🤔 왜 필요할까?

FastAPI 입문에서는 HTTP 입구를, DB 연동에서는 ORM과 Session을 배웠어요. 이번에는 기능 하나를 구현한 뒤 다른 사람이 같은 조건에서 실행하고, 저장 결과를 확인하고, 실패한 작업을 정리할 때까지 연결해요.

예제는 작은 노트 서비스예요. 시작 데이터로 환경 준비 노트가 있고, 다음 노트를 등록한 뒤 내용을 수정하고 마지막에 삭제해요. 이 입력 하나를 끝까지 사용해요.

{"title": "DB 세션을 서비스에 연결하기", "content": "요청마다 Session을 열고 닫아요."}

요청 JSON은 저장할 노트 내용이에요. Postman JSON은 이 요청을 어디로 보내고 무엇을 검사할지 담은 클라이언트 파일이에요. 이름에 JSON이 들어가도 서로 다른 역할이에요.

저장은 두 곳에 해요. notes에는 노트, changes에는 그 노트를 만들거나 바꿨다는 기록을 넣어요. changes.note_id는 notes.id를 가리키는 외래 키예요. 이 둘을 함께 확정하지 않으면 노트만 저장되고 기록은 빠질 수 있어요.

앞 방식은 기록에 실패했는데도 노트가 남았어요. 뒤 방식은 함께 취소했어요. 이렇게 DB 작업을 함께 확정하거나 함께 취소할 묶음을 트랜잭션이라고 해요. 기능의 응답뿐 아니라 저장 상태도 봐야 하는 이유예요. 실패를 낸 위치와 정리 방식은 ⑤에서 다시 봐요.

🗺️ 통째로 한 번

서비스에는 실행하기 전에 준비하는 흐름과 실행 중 요청을 처리하는 흐름이 있어요. 위에서부터 파일을 복사하는 순서만 외우면, 에러가 어느 흐름에서 났는지 놓치기 쉬워요.

언제흐름끝에서 확인하는 것
실행 전같은 Python 확인 → 설정 읽기 → DB 구조 준비 → 시작 데이터 → 검증올바른 DB와 시작 상태
서버 시작앱 생성 → 오류 처리기와 Router 등록 → 서버 수신live와 health의 차이
요청 처리Postman → Router → Service → 저장 함수 → DB → HTTP 응답상태 코드와 실제 저장값
검증 종료등록 → 재조회 → 실패 요청 → 재조회 → 수정 → 재조회 → 삭제 → 미존재 확인이번 생성 데이터 정리와 시작 수량 복귀

아래 예제는 PostgreSQL을 설치하지 않아도 흐름을 재현하도록 별도 SQLite 파일을 써요. Session과 트랜잭션을 연결하는 원리는 비교할 수 있지만, PostgreSQL의 연결 장애, 격리 수준, pgvector, 동시 수정은 이 실험으로 확인하지 않았어요.

핵심 코드는 examples/service_flow/service.py 하나예요. 오른쪽에서 단계별로 자라고, 같은 폴더의 전체 Python 파일로도 받을 수 있어요. 설정과 검증용 파일은 실행 안내에 있어요.

직접 실행하는 순서 (PowerShell)

저장소를 내려받은 뒤 examples/service_flow 폴더에서 실행해요. 처음에만 가상환경을 만들고 설정 템플릿을 복사해요. 이미 편집한 .env를 덮어쓰지 않아요.

python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
.\.venv\Scripts\python.exe service.py prepare
.\.venv\Scripts\python.exe service.py serve

브라우저에서 http://127.0.0.1:8015/docs를 열어요. 마지막 명령은 서버를 계속 실행하므로, 다른 명령은 두 번째 터미널에서 보내요. 서버 종료는 Ctrl+C예요.

🔎 한 단계씩: 설명과 코드를 나란히

코드의 ① 부분

① 실행 설정을 한곳에서 읽기

서버가 사용할 설정을 읽고, DB 파일의 위치를 한곳에서 결정해요.

환경 변수는 프로세스가 실행될 때 받는 이름과 값이에요. .env는 그 값을 파일로 적는 관례이며, Python이나 FastAPI가 모든 .env를 저절로 읽는 것은 아니에요. 이 예제는 dotenv_values()로 직접 읽어요.

왜? 터미널을 다른 폴더에서 열었다고 새 DB가 생기면, 같은 노트를 저장했는데도 다른 터미널에서는 보이지 않아요. 그래서 상대 DB 경로는 현재 터미널 위치가 아니라 service.py가 있는 폴더에 붙여요.

코드의 ② 부분

② DB 준비와 검증을 서버에서 분리하기

테이블과 시작 데이터를 준비한 뒤, 실제 저장 상태를 별도 명령으로 읽어요.

스키마는 테이블, 열, 제약처럼 DB의 구조예요. 시드 데이터는 처음 기능을 확인하기 위해 넣는 시작 데이터예요. 무결성은 외래 키 같은 관계와 규칙이 맞는 상태를 말해요.

왜? 서버가 켜질 때마다 시작 데이터를 넣거나 지우면 재시작만 해도 검증 기준이 바뀌어요. prepare는 준비, serve는 요청 처리, verify는 상태 조회로 나눠요. 서버를 켠 사실만으로 DB 준비가 끝났다고 판단하지 않아요.

코드의 ③ 부분

③ 요청마다 Session을 빌리고 돌려주기

요청마다 독립적인 작업 공간을 주고, 사용이 끝나면 DB 연결을 돌려줘요.

왜? Session을 전역 변수 하나로 공유하면 동시에 들어온 요청이 같은 작업 공간을 건드려요. 반대로 Engine을 요청마다 만들면 연결을 재사용하는 풀이 계속 생겨요. 오래 공유할 것과 짧게 쓸 것을 구분해야 해요.

객체역할이 예제의 수명
EngineDB 연결을 빌려주는 관리자. 실제 연결을 재사용하는 연결 풀을 가짐서버 프로세스 동안 공유
sessionmaker같은 설정으로 Session을 만드는 공장프로세스 동안 공유
Session읽은 객체와 변경 사항을 관리하는 작업 공간HTTP 요청마다 새로 생성
트랜잭션함께 확정하거나 함께 취소할 DB 작업의 범위쓰기 Service의 업무 한 묶음

여기서 Session은 로그인 정보를 보관하는 브라우저 세션이 아니에요. Session 객체를 만들었다고 바로 DB 연결을 점유하는 것도 아니며, 실제 SQL이 필요할 때 연결을 빌려요.

이미 시작된 트랜잭션 안에 또 begin()을 넣으면 충돌해요. Health는 자기 Session을 따로 쓰고, 일반 요청의 get_db는 Session을 전달하는 일만 맡겨요. 충돌을 숨기려고 무조건 commit()하거나 중첩 트랜잭션으로 감싸면 업무 경계가 더 흐려져요.

코드의 ④ 부분

④ 입력 계약과 저장 담당을 정하기

요청의 모양과 DB의 모양을 나누고, 저장 담당 함수에 트랜잭션 확정을 맡기지 않아요.

계약은 어떤 주소로 어떤 입력을 보내면 어떤 응답이 오는지에 대한 약속이에요. Router는 HTTP 입구, Service는 업무 순서와 규칙, Repository는 데이터를 읽고 쓰는 담당이에요. 폴더 이름 자체가 기능을 만드는 것은 아니고, 책임의 경계를 드러내는 이름이에요.

왜? 저장 함수가 혼자 commit하면 Service가 다른 작업과 묶어서 취소할 수 없어요. Router에 SQL과 업무 규칙이 다 있으면 HTTP 없이 그 규칙만 검사하기도 어려워져요.

보통 나누는 위치하는 일예제의 이름
core/config.py환경 설정config, DB_FILE
models/ORM 모델, DB 행의 구조Note, Change
schemas/HTTP 입력과 출력의 구조NoteWrite, NoteRead
repositories/조회, INSERT, 변경 기록. commit은 하지 않음require_note, insert_note, record_change
services/노트 저장과 기록을 업무 하나로 묶음⑤의 create_note, update_note
api/HTTP 입력을 Service에 전달⑥의 post_note, put_note
main.py앱과 Router, 오류 처리기를 연결⑥의 app.include_router(router)

이 페이지는 코드를 오가며 찾지 않도록 위 역할을 파일 하나의 함수와 클래스로 보여 줘요. 프로젝트가 커지면 위 위치로 옮길 수 있지만, 파일 개수를 늘리는 것이 목표는 아니에요.

코드의 ⑤ 부분

⑤ Service가 트랜잭션을 책임지기

노트와 변경 기록을 함께 확정하고, 하나라도 실패하면 둘 다 취소해요.

왜? HTTP 201을 먼저 돌려주고 나서 commit에 실패하면 사용자는 저장됐다고 믿는데 DB에는 없어요. 반대로 노트만 먼저 commit하면 변경 기록 실패를 되돌릴 수 없어요. 쓰기 작업을 묶고 commit이 성공한 다음 응답해야 해요.

note = insert_note(db, payload)실제 INSERT와 flush를 해요. 아직 다른 연결에서 확정된 저장값으로 볼 단계가 아니에요.
record_change(db, note, "created")같은 Session의 같은 트랜잭션에 기록을 추가해요.
return resultbegin 블록 바깥에 있어요. commit이 실패하면 이 줄에 도착하지 않아요.

수정도 with db.begin() 안에서 먼저 노트를 찾아요. 조회를 블록 밖으로 빼면 ③의 autobegin 때문에 이미 시작된 트랜잭션에 또 begin하려고 할 수 있어요. expire_on_commit=False는 commit 뒤에도 읽은 속성을 유지하는 설정이며, 자동 commit 설정이 아니에요.

제목 중복은 DB의 UNIQUE 제약으로 막고, 확인한 제목 충돌만 409 / TITLE_CONFLICT로 바꿔요. 모든 DB 오류를 중복이라고 처리하면 연결 장애와 프로그램 오류까지 입력 탓으로 보이게 돼요. PostgreSQL에서는 오류 코드와 제약 이름으로 원인을 분류해요.

아래 실험은 노트 INSERT가 끝난 다음 변경 기록 함수에서 예외를 냈어요. 그 뒤 별도의 Session으로 실제 DB 수량을 확인하고 정상 요청도 다시 실행했어요.

이 예제의 changes는 동작 확인용 변경 기록이에요. 노트 삭제 시 같이 지우므로, 삭제 이력도 영구 보존해야 하는 감사 로그의 설계와는 목적이 달라요.

LLM처럼 오래 걸리는 외부 요청까지 DB 트랜잭션에 넣으면 대기하는 동안 연결을 붙잡을 수 있어요. 원문과 버전을 짧게 읽고 Session을 닫은 뒤 외부 계산을 수행하고, 저장할 때 revision이 그대로인지 다시 확인하는 식으로 경계를 설계해요. 그 사이 수정과 충돌하는 정책은 별도 구현과 동시성 검증이 필요해요.

코드의 ⑥ 부분

⑥ Router와 Health를 앱에 연결하기

업무 함수를 HTTP 입구에 붙이고, 프로세스 응답과 서비스 준비 상태를 나눠 확인해요.

왜? 함수 파일이 있어도 앱에 Router를 등록하지 않으면 그 주소로 요청할 수 없어요. 서버가 응답해도 필요한 테이블이 없다면 저장 기능은 쓸 수 없어요.

코드 읽기

코드뜻

app.include_router(router)위에서 정의한 주소 묶음을 앱에 등록해요. 함수 선언만으로 별도 앱에 자동 연결되지는 않아요.

GET /live는 앱이 응답하는지만 봐요. GET /health는 자기 Session으로 DB 연결과 노트, 변경 기록 테이블 조회까지 확인해요. 여기서는 이 주소를 readiness, 즉 요청을 처리할 준비 점검으로 사용해요. Health라는 이름만으로 어디까지 검사하는지 정해지는 것은 아니에요.

HTTP 409는 제목 충돌, 422는 입력 계약 위반, 404는 노트 없음이에요. 오류 본문은 {"error": {"code": "...", "message": "..."}}로 맞췄어요. FastAPI 기본 입력 오류의 본문 모양은 다르므로 RequestValidationError 처리기도 직접 등록했어요.

실제 서버 실행은 service.py serve 명령이에요. 일반 패키지 프로젝트에서는 python -m app.main처럼 패키지를 기준으로 실행하면 import 경로를 일정하게 잡을 수 있어요. __init__.py는 일반 Python 패키지를 표시하는 빈 파일로 둘 수 있고, if __name__ == "__main__" 아래 코드는 직접 실행했을 때만 동작해요.

새 주소가 /docs에 없다면 먼저 Router 등록, 실행 중인 앱, 재시작 여부를 봐요. 다른 서버가 같은 포트에서 돌고 있으면 새 코드와 전혀 다른 응답을 받을 수 있어요.

코드의 ⑦ 부분

⑦ 클라이언트의 검증 순서를 파일로 공유하기

Postman 파일 두 개로 같은 요청 순서를 재현하고, 생성 ID를 다음 요청으로 넘겨요.

Postman은 HTTP 요청을 보내고 응답을 검사하는 클라이언트예요. Collection은 요청 URL, 방식, Body와 검사 스크립트를 묶은 파일이고, Environment는 그 요청에 채울 변수의 묶음이에요.

왜? 매번 URL과 JSON을 손으로 입력하면 생성 ID를 놓치거나, 잘못된 서버에 보내거나, 실패한 수정을 성공으로 착각해요. 요청과 기대 결과를 파일로 남기면 다른 사람도 같은 순서로 확인할 수 있어요. 이 파일이 서버나 DB를 대신 만들어 주는 것은 아니에요.

Collection JSON 다운로드 / Environment JSON 다운로드. 두 파일을 Postman의 Import로 읽고 노트 서비스 - Local 환경을 선택해요. Collection Runner에서 위에서 아래 순서로 실행해요.

파일 속 위치뜻이 예제
Collection의 item순서대로 실행할 요청 목록준비 확인부터 삭제 후 확인까지
request.method, request.url요청 방식과 주소POST {{base_url}}/notes
request.body.raw보낼 JSON을 담은 문자열title, content가 있는 노트 입력
event의 listen: "test"응답 뒤 실행할 검사 스크립트Postman 화면의 Scripts → Post-response
Environment의 values이름과 값의 목록base_url, created_id 등

URL의 {{base_url}}은 보내기 전에 선택된 변수 값으로 치환돼요. 다른 범위에 같은 이름의 변수가 있으면 우선순위 때문에 기대와 다른 값을 쓸 수 있으므로, 이 예제는 변수를 선택한 Environment에 모아요. 실제 전송 URL에 중괄호가 남아 있다면 환경 선택과 값부터 확인해요.

등록 응답에서 받은 id를 저장하고, 이후 요청은 {{created_id}}를 써요. ID를 특정 숫자로 예상하지 않아요. snapshot은 비교용으로 남겨 둔 값의 사본이에요. 여기서는 등록 또는 수정 응답을 expected_note에 저장하고 새 GET 응답과 비교해요. POST와 PUT 응답 자체도 보낸 입력과 따로 비교해요.

pm.environment.set("created_id", String(pm.response.json().id));
pm.environment.set("expected_note", JSON.stringify(pm.response.json()));
pm.test("저장값 재조회", () => {
  pm.expect(pm.response.json()).to.eql(
    JSON.parse(pm.environment.get("expected_note"))
  );
});

위 코드는 핵심을 모아 보여 준 조각이에요. 실제 파일에서는 저장 스크립트는 POST와 PUT 뒤에, 비교 스크립트는 GET 뒤에 있어요. pm.test는 검사 이름과 함수를 등록하고, pm.expect는 실제 값과 기대 값을 비교해요. to.eql은 객체 내부 필드까지 비교해요.

마지막 목록 조회시작 노트 수로 돌아왔는지이번 생성 데이터 정리 완료

삭제 직후에는 ID를 비우지 않아요. 그 ID로 GET을 보내 404까지 확인한 다음 비워요. 중간에 실패하면 남은 ID를 먼저 조회해 상태를 파악해요. seed.sql을 다시 실행하는 것은 검증용 데이터 정리와 같은 일이 아니에요.

Newman은 v2.1 형식의 Postman Collection을 터미널에서 실행하는 도구예요. 이 예제의 두 파일은 그 형식으로 만들었어요. 서버를 실행한 상태에서 같은 폴더의 두 번째 터미널로 실행할 수 있어요.

npx --yes newman run service.postman_collection.json -e service.postman_environment.json --bail

--bail은 실패 시 진행을 멈추게 해요. 중간 요청만 빼서 실행하거나 검사를 건너뛴 결과를 전체 성공으로 기록하지 않아요. Postman의 Test Results와 실패한 요청의 응답 본문을 함께 읽어요.

마지막으로 service.py verify로 DB 수량과 고아 기록도 직접 확인해요. 상태 코드와 JSON 검사, 실제 저장값, 관계 무결성은 서로 다른 증거예요. 검색 관련성이나 자연어 요약의 근거까지 자동 형식 검사만으로 확인했다고 말할 수는 없어요.
