💡 한 문장으로

Embedding은 글을 뜻이 담긴 벡터로 바꾸는 거예요. 뜻이 비슷하면 벡터가 가까워서, 글자가 하나도 겹치지 않아도 질문에 맞는 자료를 찾을 수 있어요.

🤔 왜 필요할까?

"개발용 웹 서비스는 어디서 돌리나요?"라고 물었을 때 찾아야 할 자료는 "프로젝트 폴더에서 서버를 실행합니다"예요. 글자는 하나도 겹치지 않지만 뜻은 같아요. 실제로 자료 9개에 두 방식으로 찾아보면:

Embedding은 글을 뜻이 담긴 숫자 목록(벡터)으로 바꾸는 거예요. 뜻이 비슷한 글은 비슷한 방향의 벡터가 돼서, 벡터끼리 가까운지만 재면 "뜻이 비슷한 자료"를 찾을 수 있어요. 이걸 벡터 검색(의미 검색)이라고 해요.

여기서는 한국어를 지원하는 Embedding 모델 intfloat/multilingual-e5-small을 이 PC에서 직접 돌려요.

🗺️ 통째로 한 번

자료를 벡터로 바꿔 두고, 질문도 벡터로 바꿔 가까운 순으로 고르고, 필요하면 조건으로 먼저 거르고, 많아지면 DB와 인덱스에 맡겨요. 상자를 누르면 그 단계로 가요.

코드의 ④ 부분

④ 조건으로 먼저 거르기

분류 같은 조건이 있으면, 조건 밖의 자료는 점수를 −∞로 만들어 절대 뽑히지 않게 한 뒤 Top-k를 해요.

"개발 자료 안에서만", "최신 판만"처럼 조건이 붙는 경우가 많아요. 조건을 Top-k 다음에 걸면 남는 게 거의 없을 수 있어요.

코드의 ⑤ 부분

⑤ DB로 옮기기 (pgvector)

벡터를 PostgreSQL에 저장하고, 가까운 순 정렬을 DB가 하게 해요.

자료가 수십만 개가 되면 메모리에 다 올려 두기 어렵고, 출처나 판 번호 같은 정보도 함께 관리해야 해요. pgvector는 PostgreSQL에 벡터 타입과 거리 연산자를 더하는 확장이에요.

코드의 ⑥ 부분

⑥ 많아지면: 근사 인덱스 (HNSW)

벡터용 인덱스를 만들어, 모든 자료와 비교하지 않고도 가까운 것을 빨리 찾아요.

인덱스가 없으면 질문마다 모든 벡터와 거리를 재요. HNSW는 벡터들을 "가까운 것끼리 이어진 여러 층의 그물"로 미리 엮어 두고, 그물을 따라가며 가까운 쪽으로만 찾아가는 인덱스예요. 대부분 맞게 찾지만 가끔 놓쳐서 근사라고 해요. 9개로는 차이가 안 보여서, 무작위 벡터 2만 개로 따로 재 봤어요.

코드 읽기

코드뜻
CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)코사인 거리용 HNSW 인덱스. 거리 연산자와 짝이 맞아야 쓰여요.
SET hnsw.ef_search = 10검색 때 살펴볼 후보 수 (기본 40). 크면 정확하고 느리고, 작으면 빠르고 더 놓쳐요.

🛠️ 실제로 할 때

      
상황어떻게
모델을 바꾼다벡터는 모델마다 다른 공간이라 섞어 쓸 수 없어요. 모델을 바꾸면 모든 자료의 벡터를 다시 만들어요.
긴 문서모델은 입력 길이 한도가 있어요 (e5는 512토큰). 문서는 먼저 조각으로 나눠요 (Chunking).
점수 기준선"0.8 이상이면 맞다" 같은 고정 기준은 질문마다 잘 안 맞아요. 상위 몇 개를 보여 주고, 정말 맞는지는 원문과 대조해요.
글자 검색도 필요하다제품 번호, 오류 코드처럼 정확한 글자가 중요하면 글자 검색이 더 잘 맞아요. 둘을 섞어 쓰기도 해요 (Hybrid Search).
HNSW 인덱스와 조건④처럼 조건을 같이 걸면, 인덱스가 먼저 찾은 후보를 거른 뒤라 결과가 적게 나올 수 있어요. pgvector의 hnsw.iterative_scan 설정이나 조건별 인덱스로 보완해요.
