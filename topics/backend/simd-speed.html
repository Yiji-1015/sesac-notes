SIMD와 메모리: 같은 계산이 수십 배 빨라지는 이유

백엔드 > 성능과 하드웨어

💡 한 문장으로

파이썬 반복문을 NumPy로 바꾸면 빨라지는 건, C 반복문이 SIMD로 한 명령에 여러 칸을 처리하기 때문이에요. 자료형이 좁을수록 칸이 많아지고, 메모리가 붙어 있고, 캐시에 들어가고, 임시 배열과 갈림길이 적을수록 더 빨라져요.

🤔 왜 필요할까?

"파이썬은 느리니 NumPy를 써라"는 말 뒤에는 CPU가 일하는 방식 두 가지가 있어요. 하나는 SIMD(Single Instruction, Multiple Data)예요. 요즘 CPU는 256비트(AVX2)나 512비트 레지스터 하나에 숫자 여러 개를 넣고, 명령 하나로 그 칸들을 한꺼번에 비교하거나 더해요. 다른 하나는 메모리예요. 계산보다 메모리에서 데이터를 가져오는 게 훨씬 느려서, 얼마나 붙어 있게, 얼마나 적게 읽나가 시간을 정해요.

빨라지는 이유이 쪽실무에서 보이는 곳
인터프리터 대신 C 반복문①NumPy, pandas, PyTorch를 쓰는 이유
한 명령에 여러 칸②③int8 양자화, float16 추론
붙어 있는 메모리, 캐시④⑤행렬 모양, 배치 크기, 벡터 검색 인덱스
메모리 덜 오가기⑥⑦연산 융합, 갈림길 없는 코드

터미널 프로그램 Ghostty는 입력 글자 중 특별한 문자를 찾는 반복문 하나를 SIMD로 바꿔 전체 처리량이 다섯 배쯤 늘었다고 해요. 이 쪽은 그 생각을 파이썬과 NumPy에서 재 봐요.

🗺️ 통째로 한 번

세 가지 방법 → SIMD 다섯 단계 → 자료형 폭 → 메모리 배치 → 캐시 크기 → 임시 배열 → 갈림길 없애기. 상자를 누르면 그 단계로 가요.

코드는 examples/speed/simd_numpy.py 하나예요. 시간은 PC마다 달라서, 같은 PC 안에서의 몇 배 차이를 보세요. 아래 결과는 맨 아래 실행 환경의 PC에서 잰 거예요.

코드의 ② 부분

② SIMD의 다섯 단계를 손으로

찾을 값을 32칸에 복사하고, 데이터를 32바이트씩 잘라 칸마다 비교하고, 모아서 더하고, 남은 꼬리는 하나씩 세요.

SIMD 코드는 거의 항상 이 모양이에요. ① 상수를 모든 칸에 복사(broadcast) → ② 레지스터 폭만큼씩 돌기 → ③ 칸마다 동시에 비교나 계산 → ④ 결과를 모으거나 저장(reduce) → ⑤ 폭에 안 맞는 나머지는 하나씩(scalar tail). 컴파일러가 단순한 반복문도 자동으로 이렇게 바꿔 주지 못할 때가 있어서, 아주 자주 도는 반복문은 직접 SIMD로 쓰기도 해요.

CPU마다 레지스터 폭이 달라요. ARM의 NEON은 128비트(바이트 16칸), 인텔과 AMD의 AVX2는 256비트(32칸), AVX-512는 512비트(64칸)예요. 그래서 배포할 때는 "이 CPU가 어떤 명령을 지원하나"를 실행 중에 보고 고르는 코드가 필요해요. NumPy도 그렇게 해요.

③ 자료형이 좁으면 한 번에 더 많은 칸

같은 2,000만 개 숫자를 float64부터 int8까지 바꿔 가며 최댓값과 합을 구해요.

256비트 레지스터에는 float64가 4칸, float32가 8칸, int8이 32칸 들어가요. 같은 명령 수로 더 많은 숫자를 처리하고, 메모리에서 읽을 바이트도 줄어요. 대신 표현할 수 있는 범위와 정밀도가 줄어요(모델 가볍게의 int8 양자화).

코드의 ④ 부분

④ 붙어 있는 메모리

같은 수의 숫자를 붙어 있게 두고 더할 때와 4칸씩 건너뛰며 더할 때, 행렬을 그대로 복사할 때와 전치해서 복사할 때를 비교해요.

CPU는 메모리를 한 칸씩이 아니라 64바이트 덩어리(캐시 줄)로 가져와요. 붙어 있는 데이터는 한 번 가져온 덩어리를 다 쓰지만, 건너뛰면 대부분 버려요. NumPy의 a[::4]는 복사 없이 "4칸씩 건너보기"(stride)라서 쓰기는 편하지만 이렇게 느릴 수 있어요. 자주 쓸 거면 np.ascontiguousarray로 한 번 붙여 두는 게 나아요.

코드의 ⑤ 부분

⑤ 캐시에 들어가는 크기인가

배열 크기를 32KB부터 128MB까지 늘리며 원소 하나를 더하는 데 걸리는 시간을 재요.

CPU 안에는 작고 빠른 메모리(캐시)가 여러 층 있어요. 보통 L1은 수십 KB, L2는 1MB 안팎, L3는 수십 MB예요. 데이터가 캐시에 다 들어가면 빠르고, 넘치면 훨씬 느린 RAM에서 읽어야 해요. 배치 크기나 블록 크기를 정할 때 이 경계를 의식하는 이유예요.

코드의 ⑥ 부분

⑥ 임시 배열 줄이기

같은 식을 연산마다 새 배열을 만들며 계산할 때와, 미리 만든 버퍼 하나에 이어서 계산할 때를 비교해요.

NumPy의 (x * 2 + 1) * 3 - x는 연산마다 결과 배열을 새로 만들어요. 큰 배열에서는 계산보다 이 배열들을 메모리에 쓰고 다시 읽는 시간이 더 커요. out=과 += 같은 제자리 연산으로 버퍼를 다시 쓰면 줄어요. numexpr나 JIT 컴파일러(Numba, PyTorch의 컴파일 모드)는 식 전체를 한 번에 돌려 같은 효과를 내요.

⑦ if 대신 마스크

음수를 0으로 바꾸는 일을 파이썬 if, np.where, np.maximum으로 해요.

칸마다 다른 길로 가는 코드(if)는 SIMD로 한꺼번에 하기 어려워요. 그래서 SIMD 코드는 양쪽을 다 계산하고 마스크로 고르는 방식으로 갈림길을 없애요. CPU의 분기 예측도 데이터가 무작위면 자주 틀려서 느려지는데, 마스크는 그 문제도 없어요.

🛠️ 실제로 할 때

      
상황어떻게
파이썬 코드가 느리다먼저 재요(프로파일러). 시간의 대부분을 쓰는 반복문 하나를 찾아 NumPy나 이미 있는 C 함수로 바꾸는 게 가장 큰 이득이에요. 직접 SIMD를 짜는 건 그다음이에요.
큰 배열을 다룬다자료형을 필요한 만큼만 넓게, 메모리는 붙어 있게, 임시 배열은 적게. 결과 자료형이 넓어지는지(sum의 int64)도 확인해요.
여러 하드웨어에 배포한다CPU의 SIMD 명령(NEON, AVX2, AVX-512)과 GPU, NPU 종류마다 빌드가 달라요. 파이썬 패키지도 하드웨어에 맞는 빌드를 골라 설치하는 방식(wheel variants)이 논의되고 있어요. 지원하지 않는 기계를 위한 느린 기본 경로를 꼭 남겨 둬요.
