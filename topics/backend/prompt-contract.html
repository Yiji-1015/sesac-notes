Prompt와 출력 계약: 모델의 답을 믿을 수 있게 만들기

백엔드 > LLM 활용

💡 한 문장으로

모델의 답은 언제나 그냥 글이에요. 그래서 Prompt와 근거 자료는 정해진 틀로 만들고, 받은 답은 모양 검사와 내용 검사를 거친 것만 써요.

🤔 왜 필요할까?

LLM(대규모 언어 모델)에게 질문을 보내면 답이 글로 와요. 사람이 읽기엔 충분하지만, 서비스는 그 답을 화면에 보여 주고, 근거 자료를 링크하고, 모르는 질문이면 담당자에게 넘겨야 해요. 그러려면 답이 정해진 모양이어야 하고, 그 모양을 지켰는지 프로그램이 검사할 수 있어야 해요.

예제는 "파일은 어디에 보관하나요?"라는 질문에 자료 101번("실습 파일은 개인 폴더에 보관합니다.")을 근거로 답하게 해요. 답은 이런 JSON으로 받기로 약속해요.

{"status": "answered", "answer": "개인 폴더에 보관합니다.", "source_ids": [101], "missing_information": ""}

그런데 모델은 약속을 어길 수 있어요. 여러 가지로 어긴 응답을 실제 검사 코드에 넣어 보면:

그래서 할 일은 모델에게 줄 글(Prompt)과 근거 자료(Context)를 정해진 틀로 만들고, 받은 답을 모양 검사와 내용 검사 두 겹으로 거르는 거예요.

🗺️ 통째로 한 번

자료를 고르고, Prompt를 채워 모델에게 보내고, 돌아온 글을 두 번 검사해요. 모양이 틀렸을 때만 한 번 다시 물어요. 상자를 누르면 그 단계로 가요.

이 페이지는 모델을 실제로 부르지 않아요. 모델에게 보내는 부분은 ask() 함수 하나뿐이고, 여기서는 미리 정한 응답(samples.json)을 돌려줘요. 검사 코드는 모두 실제로 실행한 결과예요. 실제 모델을 부르는 방법은 LLM API 클라이언트에서 다뤄요.

코드의 ① 부분

① 근거 자료 고르기

질문에 쓸 자료만 골라, 번호와 함께 JSON 글로 만들어요.

모델은 Prompt에 들어 있는 것만 근거로 쓸 수 있어요. 자료를 다 넣으면 길어지고 엉뚱한 자료를 섞어 쓰기 쉬워서, 질문에 맞는 것만 골라 넣어요. 이렇게 모델에게 주는 배경 자료를 Context라고 해요. 어떤 자료를 고를지는 보통 검색이 정해요 (인덱싱).

코드뜻

코드의 ② 부분

② Prompt 틀 채우기

역할, 작업, 질문, 자료, 규칙, 출력 모양을 정해진 틀에 채워요.

Prompt를 그때그때 손으로 쓰면 빠뜨리는 게 생기고, 바꿨을 때 무엇이 달라졌는지 알기 어려워요. 그래서 틀을 하나 정해 두고 빈칸만 채워요. 틀에는 무엇을 하라뿐 아니라 모르면 어떻게 하라와 어떤 모양으로 답하라까지 적어요.

코드 읽기

코드뜻
Template("... $question ...")$이름 자리를 나중에 채우는 틀 (표준 라이브러리 string)
TEMPLATE.substitute(question=..., context=...)빈칸을 채워요. 빠진 이름이 있으면 오류가 나서 실수를 막아요.

코드의 ④ 부분

④ 응답 읽고 모양 검사하기

받은 글을 JSON으로 읽고, 계약 모양에 맞는지 검사해요. 틀리면 이유를 이름으로 돌려줘요.

코드 읽기

코드뜻
json.loads(raw)글을 JSON으로. 괄호가 빠지면 ValueError

이 단계까지 실행하면

코드의 ⑤ 부분

⑤ 내용 규칙 검사하기

모양이 맞아도 내용이 약속을 어겼는지 확인해요.

모양 검사는 "번호가 정수인가"까지만 알아요. "그 번호가 내가 준 자료인가"는 이번 요청에서 무엇을 줬는지 알아야 판단할 수 있어서, 따로 검사해요.

코드 읽기

코드뜻
set(ids) <= set(provided_ids)답의 출처가 모두 내가 준 번호 안에 있나 (부분집합)
len(ids) != len(set(ids))같은 번호를 두 번 댔나
status == "answered" and (not ids or ...)답했다면 출처가 있어야 하고, 모른다면 출처가 없고 무엇이 부족한지 적어야 해요.

🛠️ 실제로 할 때

      
상황어떻게
모델에게 처음부터 모양을 지키게 하고 싶다API의 구조화 출력 기능에 ③의 스키마를 넘기면, 모델이 그 모양으로만 답하게 할 수 있어요 (LLM API 클라이언트). 그래도 ⑤의 내용 검사는 따로 해요. 모양을 지킨다고 출처가 맞는 건 아니니까요.
Prompt를 고쳐 본다한 번에 한 가지만 바꾸고, ②의 판 번호와 함께 결과를 기록해서 비교해요. 여러 개를 한꺼번에 바꾸면 무엇 때문에 좋아졌는지 몰라요.
예시를 넣고 싶다 (Few-shot)Prompt에 "이런 질문엔 이렇게" 예시를 몇 개 넣으면 모양을 더 잘 지켜요. 예시 속 답을 현재 질문에 그대로 베끼지 않게, 예시는 다른 주제로 골라요.
검사에 걸린 답사용자에게는 "답을 만들지 못했어요"처럼 안전한 문구를 보여 주고, 원래 응답과 오류 이름은 기록해 둬요. 어떤 실수가 자주 나는지 보고 Prompt를 고쳐요.

      
📦 이 코드에 쓴 라이브러리

      
단계함수하는 일
①json.dumps(), dict.fromkeys()자료를 JSON 글로 (표준 라이브러리)
②string.Template, substitute(), hashlib.sha256()틀 채우기, 판 번호
③BaseModel, Field(), ConfigDict(), Literal, Annotated, model_json_schema()출력 계약 (pydantic, typing)
④json.loads(), model_validate(), ValidationError, e.errors()모양 검사

      
build_context, parse_answer, check_rules, validate, ask, run_with_retry는 이 파일 안에서 정의한 함수예요.
